# План развития проекта (CRM/SRM сервисного центра)

Документ предназначен для планирования работ по расширению прототипа до демонстрационного продукта.  
Формулировки ориентированы на дипломную работу: SRM + онтология правил + агентный анализ + CRM/склад/заказы.

## 1) Короткий бэклог (MVP+)

### A. CRM (ремонты)
1. Карточка заказа: загрузка фото дефектов (локально, без внешних сервисов).
2. История статусов заказа: визуализация таймлайном, фильтр по изменениям.
3. Согласование: фиксация канала связи и причин отказа (список причин).
4. Платежи: таблица платежей по заказу (частичные оплаты), печать чека (HTML).

### B. Склад/запчасти
1. Поступление запчастей по закупке: автоприход в склад по `purchase_id`.
2. Связь закупки с SKU: контроль качества/гарантии, партия.
3. Списания: отмена списания/возврат запчасти в склад.
4. Уведомления: правило “низкий остаток” → автоматическое создание уведомления/нарушения.

### C. SRM + анализ нарушений
1. Разделить риск-логику: `RiskAgent` и `RepeatViolationAgent` как отдельный агент.
2. Добавить `StockAgent`: анализ склада (низкий остаток, отсутствие гарантии на SKU).
3. Добавить анализ по заказам: просрочка ремонта, отклонённое согласование, повторные обращения.
4. “Бейзлайн” и сравнение: простые эвристики vs. агентный пайплайн (для экспериментальной части).

### D. Правила (онтология)
1. UI-страница “Правила”: просмотр активных правил уже есть → добавить краткие пояснения полей.
2. Хранение правил в SQLite (опционально) + включение/выключение правил.
3. Валидация правил: проверка схемы (минимальная) + сообщения об ошибках в UI.

### E. Финансы и зарплата
1. Доход/расход/прибыль по заказу (работа + запчасти − закупка).
2. Отчёт по мастерам: фикс/процент, сумма к выплате за период.
3. Дебиторка: список клиентов с задолженностью.

### F. Документы
1. Шаблоны печати: добавить реквизиты организации (из `.env`/настроек).
2. Экспорт в PDF (опционально): локально через headless-печать браузера, без платных сервисов.

### G. Тестирование и CI/CD
1. Расширить тесты: CRUD клиентов/заказов/склада, роли.
2. Smoke test веб-приложения: запуск Uvicorn + запрос `/health`.
3. Отчёт по покрытию (опционально): `pytest --cov`.

## 2) Гипотезы для вычислительного эксперимента (Задание 7)

1. Разделение анализа на специализированных агентов повышает полноту выявления нарушений при сопоставимой точности.
2. Онтологическая модель правил снижает “стоимость изменения” требований (время на добавление правила) по сравнению с жёстко прошитой логикой.
3. Порог повторяемости нарушений корректно выявляет рискованных поставщиков при шуме в данных.

## 3) Риски/ограничения (для дипломной)

- SQLite подходит для локального прототипа; при серверном развёртывании потребуется миграционная стратегия.
- В прототипе не реализована внешняя интеграция (SMS/e-mail) — только имитация уведомлений.
- Права доступа упрощены (роль-based), без тонких пермишенов на уровне объектов.
